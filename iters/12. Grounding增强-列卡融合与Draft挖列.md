# 12. Grounding 增强施工方案（AskData 启示 × 现有 RC）

> 日期：2026-08-04 | 分支：`prepare_for_bird_test`  
> 承接：iter8（榜单 insight）+ AskData 论文读后 + 投影对齐线收束（iter6/10/11，commit `2398069`）  
> 基线：held-out smoke rc100 官方 EX **78/100**；对齐器 / 投影 few-shot **已放弃**（默认 off）

---

## 0. 一句话

AskData 的启示不是「我们没做 profiling」，而是：**统计真相已有，尚未焊进统一列卡，linking 仍偏点名而非从草稿 SQL 回收列。**  
本 iter 只动 **grounding**（元数据呈现 + schema 召回），不重开投影专模、不上 query-log 大工程。

## 2. 目标架构（目标态）

```text
DB + column_meaning.json
        │
        ▼
┌──────────────────────────────┐
│ RC gen / enrich（现有）       │  stats + quality + FK card
│ + ColumnCard 融合（新）       │  meaning ∪ stats → 一列一卡
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ Schema Linking（增强）        │
│  1) one-shot 选表（现有）     │
│  2) FK expand（现有）         │
│  3a) LLM refine（现有，可留） │
│  3b) Draft-SQL 挖列（P1 新）  │  1～2 次草拟 → 并集列 → 高 recall
└──────────────┬───────────────┘
               ▼
        ReAct + verify_sql（流程编号不变）
```

原则（对齐器教训）：**只加静态上下文或 linking 前置步骤；不新增 ReAct 工具、不改 workflow 步号、不挤 verify。**

## 3. 施工包（按 ROI）

### P0 — 列卡融合（优先，预计 1～2 天）

**问题**：`column_meaning` 与 profiling 是两段拼盘，模型注意力分散；枚举/脏值与官方释义未对齐。

**做：**

1. 定义 `ColumnCard`（或等价结构）：  
   `name | type | meaning(官方优先) | null% | top-k/samples | quality one-liner | FK hint`  
2. 在 **导出层**融合（优先改 `ExportToCompactPrompt` / 或 `ColumnMeaningStore.FormatForDB` 改为吃 SharedContext）：  
   - 有 meaning → 释义一行 + stats 一行  
   - 无 meaning → 仅 stats（行为与今天接近）  
3. Leaderboard 打开 column_meaning 时，**去掉重复的第二段 dump**，只保留融合后的列卡（控 token）  
4. 开关：`EnableColumnCardFusion`（默认 leaderboard=on，可关做消融）

**验收：**

- 单库目视：`frpm`/`legislator` 等列同时出现释义 + top-k  
- smoke l20 不掉 EX / verify 率；再打 rc100  
- diff prompt 长度：融合后应 ≤ 当前「RC + 整块 meaning」或略短

**非目标：** 重跑 Phase2 LLM 笔记；不强制全列 NL 重写。

---

### P1 — Draft-SQL 任务对齐挖列（AskData Schema Linking）

**问题**：`RefineRelevantColumns` 是「点名列」；LLM 更擅长「写 SQL」再回收引用列。

**做：**

1. Linking 选表 + FK expand 之后，增加可选一步 `MineColumnsFromDraftSQL`：  
   - Prompt：当前题 + evidence + **已选表的列卡**（不要全库）  
   - 采样 1～2 条「草稿 SQL」（允许错，只要引用列）  
   - 解析标识符 → 与表列做大小写不敏感匹配 → **并集**进 focused schema  
2. 与现有 `RefineRelevantColumns` 关系：  
   - 默认 **并集**（高 recall）；或 `draft_only` / `refine_only` 消融  
3. **不**把草稿 SQL 交给主 ReAct 当答案；草稿仅用于挖列后丢弃  
4. 开关：`EnableDraftColumnMine`；次数 `DraftMineN=1`（先 1，再试 2）  
5. Token/延迟：草稿用短 schema；失败/空解析 → 静默回退 refine-only

**验收：**

- 日志：`draft_mine: tables=… cols=+N`  
- 对照同一 100：漏列/错表类错是否下降；verify 率不掉  
- 若 EX 无增益且延迟 +>15% → 关默认，仅留代码消融

**风险：** 草稿带偏后续 SELECT（投影污染）。缓解：主 prompt **不展示草稿 SQL**；只扩列集合。

---

### P2 — 全列 profiling→短 NL（可选，P0/P1 有增益后再做）

**做：** 离线 batch：对缺失 meaning 的列，用「stats 块 → 一句 ≤40 token 语义」写入 RC `business_notes` 或 `column_nl`。  
**触发：** P0 融合后仍有大量「无释义 + 高混淆」列。  
**不做：** 替代官方 meaning；不在线每题现生成。

---

### P3 — 后置（本 iter 不排期）

- MinHash / 值重叠补 FK  
- Query log 挖 join / SQL-to-text few-shot（真生产再开）  
- Agentar 式 selector / 大规模 test-time scaling（另开 iter）

## 4. 评测协议（强制）

```bash
# 基线对照
results/bird/heldout_v1_smoke_leaderboard_rc100/   # EX 78

# 建议输出目录命名
results/bird/heldout_colcard_rc100/      # P0
results/bird/heldout_draftmine_rc100/   # P1

# 官方 EX
go run ./cmd/eval_ex \
  --predict results/bird/heldout_*/predict.sql \
  --gold benchmarks/bird/heldout_v1_smoke_private/gold.json \
  --db-dir benchmarks/bird/heldout_v1_smoke/test_databases

# 护栏（每轮）
# verify 调用率、配对翻转、prompt 是否仍含 MANDATORY verify_sql
```

跑法：优先 **tmux 会话**，勿用会随 agent 会话回收的裸 `nohup &`。  
对齐器保持 `PROJALIGN_MODE=off`；不设 `PROJ_FEWSHOT_PATH`。

小烟：先 `limit 20`，护栏过再 100。
